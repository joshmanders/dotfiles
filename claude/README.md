# Claude Code Configuration

Claude Code settings and skills for consistent AI assistance.

## Two `claude` directories — read this first

There are two distinct Claude configuration directories in the dotfiles repo. They look similar and are easy to confuse:

| Directory             | Scope     | Symlinked to    | Purpose                                                                                                   |
| --------------------- | --------- | --------------- | --------------------------------------------------------------------------------------------------------- |
| `$DOTFILES/claude/`   | Global    | `~/.claude/`    | Source of truth for **global** rules, skills, agents, settings. Applies in every project.                  |
| `$DOTFILES/.claude/`  | Project   | (not symlinked) | **Project-scoped** rules and skills for working with the dotfiles repo itself. Only loads when CWD is inside the repo. |

`$DOTFILES` is exported by the dotfiles config and points at the repo root (defaults to `$HOME/.files`). Use it in references so paths don't break if the repo lives elsewhere.

When you add a rule or skill, ask: *does this apply everywhere, or only when editing this repo?* Universal guidance goes in `claude/` (global). Dotfiles-specific maintenance goes in `.claude/` (project).

## Files

| File                     | Purpose                                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------- |
| `CLAUDE.md`              | Main instructions (symlinked to `~/.claude/CLAUDE.md`)                                        |
| `rules/`                 | Modular rules (symlinked to `~/.claude/rules/`)                                               |
| `skills/`                | Custom skills (symlinked to `~/.claude/skills/`)                                              |
| `agents/`                | Subagent definitions (symlinked to `~/.claude/agents/`)                                       |
| `hooks/`                 | Hook scripts and their configs. Referenced by absolute path from `settings.json`, not symlinked. |
| `install.d/`             | Install-time hooks. Sourced before the settings render to export template variables.           |
| `settings.json.template` | Template with `${DOTFILES}` placeholders. The installer renders it into `settings.json`.       |
| `settings.json`          | Generated by the installer. Gitignored. Symlinked to `~/.claude/settings.json`.                |
| `keybindings.json`       | Custom keybindings (symlinked to `~/.claude/keybindings.json`)                                |

## Installation

```bash
bash claude/install.sh
```

This will:

1. Create `~/.claude` directory if needed
2. Render `settings.json.template` → `settings.json` with the actual `$DOTFILES` path substituted in
3. Symlink `CLAUDE.md` → `~/.claude/CLAUDE.md`
4. Symlink `rules/` → `~/.claude/rules/`
5. Symlink `skills/` → `~/.claude/skills/`
6. Symlink `agents/` → `~/.claude/agents/`
7. Symlink `settings.json` → `~/.claude/settings.json`
8. Symlink `keybindings.json` → `~/.claude/keybindings.json`

### Why `settings.json` is generated

The settings file contains absolute paths (the `DOTFILES`/`BASH_ENV` env vars and a hook command). Hardcoding them in the committed file would tie the install to one specific clone location. The template uses `${DOTFILES}` placeholders that the installer substitutes with the actual path at install time, so the dotfiles repo can live anywhere.

### The render replaces the file

Every install overwrites `settings.json` from the template, so the template is the only source of truth — delete a key there and it's gone after the next install. Settings here are curated by hand against `settings.reference.md`, and a merge would make deletions impossible to express.

The cost is that anything Claude Code wrote into `settings.json` itself is discarded. In practice that's `remote.defaultEnvironmentId`, which is cheap to lose: selecting a cloud environment writes it back, and a stale id would be worse than a missing one. It stays out of the template deliberately — the template is committed, this repo is public, and the value is account-scoped.

## Customization

### Add a new skill

1. Create directory: `skills/my-skill/`
2. Add `SKILL.md` with frontmatter:
   ```yaml
   ---
   name: my-skill
   description: When to use this skill
   ---
   ```

Skills are automatically available since the folder is symlinked.

### Edit instructions

Modify `CLAUDE.md` directly. Changes apply to all Claude Code sessions.

### Add keybindings

Edit `keybindings.json`:

```json
{
  "bindings": [{ "key": "ctrl+s", "command": "submit" }]
}
```

### Change settings

Edit `settings.json.template` (not the generated `settings.json`, which gets overwritten by the next install). Re-run `bash claude/install.sh` to regenerate.

#### Permissions

Uses `bypassPermissions` mode — all commands auto-approved. Security enforcement is handled by the PreToolUse guard hook (`claude/hooks/guard.sh`) which blocks dangerous commands via regex patterns in `claude/hooks/denied-commands.json` (72 patterns).

Protected directories (`.git/`, `.claude/`, `.vscode/`, `.idea/`, `.husky/`) still prompt on write even in bypass mode.

## Hooks

| Event              | Handler                         | Purpose                                                                       |
| ------------------ | ------------------------------- | ----------------------------------------------------------------------------- |
| `PreToolUse`       | `hooks/guard.sh` (command)      | Blocks dangerous Bash commands. Config: `denied-commands.json`.               |
| `UserPromptSubmit` | `hooks/skill-gate.sh` (command) | Routes a request to the skill that must run first. Config: `skill-gate.json`. |
| `Stop`             | agent, `hooks/claim-check.md`   | Verifies the factual claims in the reply against the transcript. **Not enabled** — see below. |

Two of these exist because instructions alone don't reach the assistant at the moment they're needed.

**`skill-gate`** fires before the reply starts. `brainstorming` and `systematic-debugging` were previously invoked only if the assistant decided to invoke them — and the moment either is needed is the moment it has concluded it isn't. The hook matches the incoming prompt against `skill-gate.json` and injects a directive naming the skill. First match wins, so key order in that file is priority order.

**`claim-check`** fires when the reply is finished but before it's read. It receives the transcript from the harness — the assistant doesn't assemble it, filter it, or get asked, which is the whole point: a check fed by the thing it's checking is worthless. The agent is read-only and must never re-run a command from the transcript.

Its prompt lives in `hooks/claim-check.md` so it stays readable in a diff, and `install.d/claim-check-prompt.sh` embeds the file's contents into `settings.json` at install time. Embedding rather than pointing at the path matters: a referenced file is one the verifier has to choose to open, and can fail to open or decide it doesn't need. Edit the markdown, re-run the installer.

**It is not wired into the template.** In live use it took over two minutes per turn, because it was reading the entire session transcript to check a single message. `claim-check.md` now scopes it to the last message and the current turn, but that hasn't been measured yet. Enable it by adding this alongside the other events in `settings.json.template` and re-running the installer:

```json
"Stop": [
  {
    "hooks": [
      { "type": "agent", "prompt": "${SCRUTINY_AGENT_HOOK_PROMPT}", "timeout": 300 }
    ]
  }
]
```

Watch the turn time on a short session before leaving it on.

Both command hooks are tested. Run `hooks/guard.test.sh` and `hooks/skill-gate.test.sh`.

## Install hooks

`install.d/*.sh` is sourced by `load_install_hooks` (see `lib/README.md`) before `settings.json` is rendered. Each hook exports variables the template references as `${VAR}`.

The render expands every `${VAR}` from the environment using `perl` rather than `sed`, because the expansions include JSON-escaped text whose backslashes `sed` would reinterpret. A variable the template references but no hook exported is a hard error, so a missing hook fails the install instead of quietly rendering an empty prompt. The result is validated as JSON before it replaces `settings.json` — a malformed one would disable Claude Code entirely.

See `claude/settings.reference.md` for the full settings reference.
